# Format Security Matrix

**Document ID:** PW-FORMAT · **Version:** 0.2.0 · **Status:** Initial profile; no decoders enabled · **Reviewed:** 2026-11-14

This is a planning matrix, not a promise of support. Exact specifications and decoder versions must be researched and pinned before implementation. File signatures are partial identifiers and must be combined with structure parsing and policy. All formats default to no automatic native decoder enablement. `Core` means initial byte-inspection priority only.

## Policy and adapter gate

Current implementation note: the matrix describes an incomplete profile, not full-format support. JS covers bounded structural profiles for JPEG, PNG, GIF, WebP, plus SVG static-profile processing. PHP is independently native and currently covers bounded marker/segment traversal for JPEG; limited PNG/GIF/WebP structure, PNG chunk CRCs, chunk type and critical-chunk checks, IHDR parameter combinations, indexed-color palette requirement and contiguous IDAT ordering, WebP RIFF chunk lengths/zero padding and selected VP8X reserved fields, selected dimensions/frame caps, partial EXIF TIFF directory inspection on JPEG/PNG/WebP, indicator-only signatures in selected metadata/extension/trailer regions, and an ext-dom-based static SVG profile. Neither runtime includes a raster decoder. Capability reports and partial coverage are authoritative for each runtime.

An adapter proposal must name exact parser/decoder, versions and transitive native libraries; upstream security policy; supported subfeatures; format corpus; fuzz target; resource enforcement; license; platform/build matrix; sanitization fidelity; and whether its capability is equal in PHP and JS. A PHP GD decoder is build-dependent (PHP docs enumerate supported types conditionally); ImageMagick requires an explicit restrictive policy. These are candidates only, not dependencies selected by this baseline.
